- Preserve the supplied procedural Kage renderer as a browser-only module using its compatible Three.js version; this retains the user's exact scene rather than substituting a different visual.
- Keep portfolio text in a root React context fed by the published content (Cloudflare KV, read by the root route loader; built-in defaults when nothing is published). The Studio at /studio is a real admin: password login (secrets ADMIN_PASSWORD and SESSION_SECRET), signed HttpOnly session cookie, server-side validation (src/lib/content-schema.ts), versioned saves with conflict detection, and revisions. Local previews live in memory only; the Studio draft autosaves to session storage. All admin code lives in src/backend and is reached via /api/studio/* from src/server.ts; keep it free of framework APIs and never log secrets.
- Attach the achievement tome to the scene camera, fit it to the camera frustum, and render it on an isolated foreground layer; this keeps enlarged pages readable and prevents scenery from covering the book.
- Legacy `achievements` stay at the fixed 15-leaf shape only for backward compatibility; the canonical Book (content.book) has no fixed page count, and once it exists it is the only source the book surfaces read.
- Sample one shared terrain height field for the mountain mesh and name-letter baselines; this grounds the lettering on matching slopes rather than a flat overlay.
- Keep the supplied scene's color grade without screen grain, chromatic aberration, bloom blur or adaptive resolution reduction; this preserves sharp rendering.
- Book data lives in one canonical model (src/lib/book/model.ts: Book → ordered Pages → text/image/shape Elements on a fixed 768×1024 logical page). Legacy `achievements` leaves are migrated on read by resolveBook() (leaf i → pages 2i/2i+1, plus a final contact page) so older stored content never loses data; this lets every surface share one data shape.
- Book JSON holds only ImageRef keys ("url:" now, "r2:" later) resolved through src/lib/book/image-store.ts; inline/binary image data is rejected by server-side validation (src/lib/book/validate.ts) to keep KV small and ready for R2.
- All page pixels come from one renderer, paintPage() in src/lib/book/render.ts (Canvas 2D, seeded paper grain): the 3D tome textures, the Studio Book Editor canvas, thumbnails and Preview all call it, so identical JSON renders identically everywhere. Editor-only UI (selection, handles, guides, inline textarea) is an overlay and never draws into page pixels.
- Book Editor edits are invertible Ops (src/lib/book/ops.ts) with Studio-owned undo/redo history (passed to BookEditor as props so it survives switching tabs; cleared by the Studio whenever it replaces the whole book); they write into the existing Studio draft (debounced session-storage autosave + versioned publish with conflict detection), never a separate save path. The editor bundle is lazy-loaded by the Studio so the public site never downloads it.
- Chapter integration caches layout on refresh and sends raw progress to the scene; only the scene frame loop damps camera/book progress, avoiding stacked smoothing and per-scroll layout reads.
- Scene quality policies live in a browser-safe pure module with tests; use a fixed device-appropriate DPR, never adaptive resolution, to preserve sharp rendering.
- Sessions are stateless signed cookies, but sign-out is enforced on the server: logout stores the session nonce as revoked in KV, and "sign out of all devices" stores a revoked-before timestamp (src/backend/store.ts). Every authorized request checks both, and a session that cannot be checked (no KV) is not trusted. Revocation is as consistent as KV (about a minute).
- Request bodies are size-capped while streaming, in bytes (MAX_CONTENT_BYTES in content-schema.ts is the one limit shared by the server and the Studio's Import); the unauthenticated login body is capped at 4 KB.
- Public-site wording and SEO live in content.site (SiteText), edited in the Studio's "Site text & SEO" tab; title/description come from the root route head only. Do not hard-code visible text or the owner's name in components: use content.name / content.site. `name` and `wordmark` are required (the 3D lettering draws exactly the stored wordmark; the legacy value "NAZMUL" is upgraded on read in store.ts).
- Once content.book exists it is the source for the book, so the Contact & links fields are pushed into the contact page by element role with syncContactFields() (src/lib/book/migrate.ts), and bookTitle into book.title. Links placed on book pages are exposed as real <a> elements by pageLinks() (render.ts) under the book; the 3D pixels themselves are not clickable.
- Book image links are https only (plain http is blocked as mixed content) and the host must allow CORS for the canvas.
- Publishing can carry a one-line note (cleanNote(), max LIMITS.note) stored on the version record and kept on the revision it becomes; records saved before notes read as having none. describeChanges() (src/lib/content-diff.ts) is the single place that turns two contents into the "what changed" list used by the Studio's change panel, Ctrl/Cmd+S confirmation and the version-history comparison; keep it in step when adding content fields (it is deliberately explicit, not a generic JSON diff).
- Link-preview image comes from content.site.ogImage (https only) or the bundled /og-image.jpg, set in the root route head only.
- Uploaded images live in the MEDIA R2 bucket (src/backend/media.ts), reached only through the Worker: POST /api/studio/upload (auth + same-origin + streamed size cap) takes raw image bytes, identifies them from the bytes (src/lib/media.ts imageInfo: JPEG/PNG/WebP/GIF only, SVG refused, pixel limits) and stores them under a content-hash name; GET /media/<name> (public, only valid hash names, type from the extension, nosniff, immutable) serves them from the site's own origin, which is why the 3D book can read them without CORS. Image refs are "media:<name>" keys (src/lib/book/image-store.ts); site.coverImage must be one, site.ogImage may be one or an https link. Never trust a client-claimed type or filename, never serve anything but the four formats, never accept a name that is not a hash.
- Deleting an image is refused (409 in_use) while the published content uses it (mediaUsage in src/lib/media.ts); the Studio's Media tab also blocks it for the draft. Export/Import JSON carries references only, not image bytes.
- scripts/deploy-cloudflare.mjs creates the bucket and binds it as MEDIA; a failure there (R2 not enabled, token lacks permission) must only warn: the deploy must never be blocked by images (interpretBucketCreate in scripts/r2-bucket.mjs).
- R2 is where images belong, but an upload must never fail just because R2 is missing or errors: src/backend/media.ts storeImage() then keeps the image in the CONTENT KV namespace (key "media/<name>", metadata {type,size,uploaded,width,height}) under the SAME name, so the same "media:<name>" ref and /media/<name> address work. The upload response carries storage: "kv" and fallback: "r2_not_connected" | "r2_error"; the Studio must show describeStorageFallback() (a "warn" notice, plus the editor's toolbar line and the Media tab banner). Serving tries R2 first then KV; re-uploading while R2 works, or POST /api/studio/media/migrate ("Move to R2", a batch of MIGRATE_BATCH per call), moves images into R2, and a KV copy is only deleted after R2 is confirmed to hold the object. Delete/list cover both stores; an R2 failure must not look like "not found". Only when both stores fail is the upload refused (502 storage_failed).
